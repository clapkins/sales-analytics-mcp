# PLAN.md — план реализации

Работа идёт этапами. Каждый этап заканчивается коммитом. К следующему этапу переходим только когда выполнены все пункты «Готово, когда».

Перед началом каждого этапа: сформулируй, что собираешься сделать, и дождись подтверждения пользователя. После завершения: покажи, что получилось, и отметь этап как выполненный в этом файле.

## Этап 0. Проверка связки с MCP-клиентом

**Зачем:** убедиться, что сервер вообще подхватывается клиентом, до того как написан хоть какой-то полезный код. Если конфиг не работает, узнать об этом надо сейчас, а не на пятом часу.

**Что сделать:**
- Инициализировать проект: `pyproject.toml`, `.venv`, `.gitignore`, git-репозиторий. По ТЗ репозиторий должен быть **открытым** на момент сдачи — работать можно в приватном, но перед отправкой обязательно перевести в public и проверить ссылку из режима инкогнито.
- Написать минимальный MCP-сервер на FastMCP с единственным инструментом `ping()`, возвращающим строку.
- Подготовить конфиг для MCP-клиента (Claude Desktop / Cherry Studio) с корректными путями под Windows — абсолютные пути, экранированные обратные слэши.
- Показать пользователю конфиг и инструкцию, куда его положить.

**Готово, когда:**

- Дальше без этого подтверждения не идём.

**Коммит:** `feat: каркас проекта и минимальный MCP-сервер`

## Этап 1. Тестовые данные

**Что сделать:**
- `scripts/generate_data.py` — генератор синтетического датасета.
- Датасет: ~180 строк, период 2023–2024, колонки `Date, Product, Region, Sales, Quantity, Profit`. 5–6 продуктов, 4 региона.
- В данные намеренно закладываются дефекты, иначе очистке нечего чистить:
  - ~7% пропусков в `Sales` и `Profit`;
  - 5 полных дублей строк;
  - 3–4 выброса по `Sales` (на порядок выше нормы);
  - разнобой в формате дат (`2023-05-14`, `14.05.2023`, `05/14/2023`);
  - лишние пробелы и разный регистр в `Region`.
- В данных должна быть различимая сезонность и заметная разница между регионами — иначе выводы LLM получатся водянистыми.
- Результат сохранить в `data/sales_data.csv`, зафиксировать `random_state`.

**Готово, когда:**
- Файл `data/sales_data.csv` существует и воспроизводимо генерируется скриптом.
- В README позже будет упомянуто, что данные синтетические и как их пересоздать.

**Коммит:** `feat: генератор тестовых данных и датасет sales_data.csv`

## Этап 2. Ядро: реестр, сессия, базовый скилл

**Что сделать:**
- `core/session.py` — хранилище датасетов в памяти: `put(df, meta) -> dataset_id`, `get(dataset_id) -> df`, `list()`. Осмысленная ошибка при неизвестном `dataset_id` со списком доступных.
- `core/registry.py` — реестр скиллов: базовый класс `BaseSkill` (поля `name`, `description`, метод `run`), декоратор `@register_skill`, автодискавери всех модулей пакета `skills/` через `pkgutil`.
- `core/errors.py` — единый формат ошибки для LLM: код, человекочитаемое сообщение, список допустимых значений, предложение исправления.
- `core/config.py` — пути к папкам `charts/`, `reports/`, `data/`.

**Готово, когда:**
- `python -c "from core.registry import discover; print(discover())"` печатает пустой список без ошибок.
- Есть тест: регистрация фиктивного скилла и его обнаружение реестром.
- Ни один модуль в `core/` не импортирует конкретные скиллы.

**Коммит:** `feat: ядро — реестр скиллов, session store, формат ошибок`

## Этап 3. Скиллы загрузки, статистики и очистки

**Что сделать:**
- `skills/loading.py` → `DataLoadingSkill`: CSV/Excel/JSON, автоопределение разделителя и кодировки (обязательно пробовать `utf-8`, `utf-8-sig`, `cp1251`), приведение типов, парсинг дат из разных форматов. Возвращает `dataset_id`, размерность, типы колонок, количество пропусков по колонкам, 3 строки примера.
- `skills/describe.py` → `DescriptiveStatsSkill`: базовая статистика — по числовым колонкам среднее, медиана, стандартное отклонение, квартили, min/max; по категориальным — число уникальных значений и топ-5 по частоте; по датам — диапазон периода. Это владелец инструмента `describe_data` из ТЗ, без него инструмент повиснет без реализации.
- `skills/cleaning.py` → `DataCleaningSkill`: удаление дублей, заполнение пропусков (медиана для чисел, мода для категорий), нормализация текстовых колонок (пробелы, регистр), детекция выбросов по IQR с параметром — помечать или удалять.
- Ключевое: скилл возвращает **лог операций** — что именно и в каком количестве было сделано. Этот лог потом попадёт в отчёт.
- Очистка создаёт новый `dataset_id`, исходный датасет остаётся доступен.

**Готово, когда:**
- На `data/sales_data.csv` загрузка отрабатывает без ручных подсказок по кодировке и формату дат.
- Очистка находит все заложенные на этапе 1 дефекты: 5 дублей, ~7% пропусков, выбросы.
- Есть тесты на оба скилла.

**Коммит:** `feat: скиллы загрузки и очистки данных`

## Этап 4. Скиллы визуализации и генерации выводов

**Что сделать:**
- `skills/visualization.py` → `VisualizationSkill` с типами графиков: `trend` (динамика по времени), `distribution` (гистограмма), `correlation` (тепловая карта), `top_n` (столбчатая по категориям).
- Требования к графикам — это отдельный критерий оценки: заголовок, подписи осей с единицами измерения, легенда где нужна, читаемый шрифт, единая цветовая палитра на весь проект, `dpi=150`, сетка. Никаких дефолтных серых matplotlib-графиков.
- Каждый график сохраняется в `charts/` с осмысленным именем и возвращает: путь, тип, и **текстовое описание того, что на нём видно** (диапазон значений, тренд, выбросы) — модель картинку не видит.
- `skills/insights.py` → `InsightGenerationSkill`: собирает статистику, лог очистки и описания графиков в структурированный контекст для LLM. Сам текст выводов не пишет — формирует материал, из которого его напишет модель.

**Готово, когда:**
- Все четыре типа графиков строятся на тестовых данных и визуально приемлемы (покажи пользователю PNG перед коммитом).
- Описания графиков содержательны, а не шаблонны.

**Коммит:** `feat: скиллы визуализации и подготовки выводов`

## Этап 5. Слой MCP-инструментов и второй транспорт

**Что сделать:**
- `server.py` — инструменты, сгенерированные из реестра скиллов. Имена обязательно как в ТЗ: `load_data`, `describe_data`, `plot_trend`, `plot_distribution`, `correlation_analysis`.
- Дополнительные инструменты: `list_datasets`, `auto_analyze` (сама выбирает тип графика по типу колонки), `export_report(dataset_id, format)`.
- Описания инструментов и параметров пишутся так, чтобы модель выбирала их правильно без подсказок — это часть критерия «интеграция с LLM».
- Уточняющие вопросы: если для графика не хватает данных (не указана колонка, неоднозначный выбор) — инструмент возвращает не ошибку, а список вариантов, чтобы модель спросила пользователя.
- Два транспорта: `server_stdio.py` и `server_http.py` (streamable-http). Выгрузить OpenAPI-спецификацию HTTP-варианта в `openapi.json` — она нужна для интеграции через Custom GPT Action.
- `prompts/system_prompt.md` — инструкция для LLM с описанной последовательностью шагов анализа: загрузка → структура → статистика → очистка → графики → выводы. Это прямое требование пункта 4 ТЗ («описать в системном промпте последовательность шагов»), не пропускай его. Тот же текст продублировать как MCP-примитив `prompt` на сервере, чтобы клиент подтягивал его автоматически, и вставить в README как инструкцию для Custom GPT.

**Готово, когда:**
- Клиент видит весь список инструментов с корректными схемами.
- `openapi.json` лежит в репозитории.
- Вызов инструмента с заведомо неверным именем колонки возвращает подсказку с допустимыми значениями, а не трейсбек.

**Коммит:** `feat: слой MCP-инструментов, stdio и http транспорты, OpenAPI`
